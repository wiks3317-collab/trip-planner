# v21p3 更新說明（安全性強化）

本版在 v21p2 基礎上進行權限邊界收緊，版本仍維持 GitHub Free + GitHub Pages + Firebase Serverless 架構。

### v21p3 主要變更
- **移除舊行程「我是原統籌人，進行資料銜接」功能**：前端不再提供 `claimLegacyTrip()`、認領按鈕或相關事件處理。
- **Firestore Rules 移除 Legacy Claim 寫入通道**：舊行程（缺少 Auth Model v2 欄位）不再允許一般登入使用者自行認領。
- **未完成身份模型的舊行程改由管理員處理**：一般使用者無法直接讀取舊行程主文件；需要保留的資料可由管理員檢查、匯出或依既有管理流程重新建立。
- **收緊行程主文件讀取權限**：`trips/{tripId}` 不再對所有已登入使用者開放 `get`；只有已綁定 `access` 的成員與系統管理員可讀取。
- **邀請加入改為最小揭露**：未綁定使用者透過有效邀請連結提出加入申請時，Rules 只驗證邀請碼與行程的對應關係，不需要先讀取整份行程成員名單。
- **補強 owner 一致性**：新建／更新的 v2 行程要求 `access[ownerUid] == 'owner'`。

### 安全性影響
這次調整後，即使攻擊者知道 `tripId` 並已登入 Google，也不能僅靠知道 ID 讀取行程的 `members`、`access`、`ownerUid`。有效邀請連結只用於提出加入申請，不等於立即取得行程讀取或編輯權限；仍須由統籌人核准。

## v21p2 修正版

- 修正 GitHub Pages 部署時 `admin-firebase-config.js` 與 `admin.html` 內容錯置造成管理後台整頁空白的問題。
- `admin.html` 改為只載入 `admin.js`，由 `admin.js` 統一引用 Firebase 管理員設定。
- Firebase 管理員設定檔恢復為純 JavaScript 模組，不再包含任何 HTML/CSS。
- `admin.js` 與設定檔加入 `v=21p2` 版本查詢字串，降低 GitHub Pages／瀏覽器快取舊檔造成問題的機率。
- 管理後台模組載入失敗時，頁面會顯示錯誤提示，不再呈現無訊息的空白頁。

## v21：12 碼代碼輸入與管理員成員／邀請連結管理

### 本版完成

- **使用者可直接輸入 12 碼邀請代碼加入行程**：支援完整邀請網址與單獨 12 碼代碼；6 碼舊版邀請代碼不再被當成可加入行程的輸入。
- **邀請代碼改為純系統產生**：使用者頁面與管理員頁面不提供手動修改代碼的欄位；12 碼代碼與完整網址改為純文字呈現並提供複製功能。到期時間、次數上限與標籤仍可管理，但代碼本身不可修改。
- **系統管理員建立邀請連結**：具有 `canEdit: true` 且通過重新驗證的管理員，可以在指定行程直接建立新的 12 碼邀請連結；建立動作寫入 `adminAuditLogs`。
- **系統管理員新增成員**：具有 `canManageMembers: true` 的管理員，可新增成員、設定姓名、owner/editor/viewer 權限及 UID；同一 UID 不可重複綁定，owner 仍必須恰有一位且至少綁定一個 UID。
- **管理員成員編輯介面補強**：修正權限選擇未完整回寫草稿的問題，並新增成員移除功能；高風險成員／UID變更仍要求 15 分鐘內重新驗證。

### 第 3 項權限評估

系統管理員的「新增成員／設定權限／UID」屬於高風險權限，因為它可以直接決定誰能查看、編輯或管理行程。因此不建議只要 `isAdmin` 就能操作；本版沿用獨立的 `canManageMembers` 權限，並要求近期重新驗證。

「建立邀請連結」則與 `canEdit` 的既有管理範圍較一致，但邀請連結本身會讓持有連結的人進入行程，因此本版同樣要求 `canEdit` + 近期重新驗證，並寫入管理員稽核紀錄。系統仍禁止管理員列舉所有 `shortlinks`，避免為清理同步碼而暴露其他使用者的同步資料。

## v20：邀請連結管理與舊版 6 碼連結清理

### 本版完成

- **系統管理者行程詳情新增「邀請連結」區塊**：可查看每組邀請連結的用途、6/12 碼版本、使用中／已過期／已撤銷狀態、到期時間、已核准次數、剩餘次數、建立時間與完整連結。
- **系統管理者編輯權限**：具有 `admins/{uid}.canEdit: true` 的管理員，可調整邀請連結標籤、到期時間與次數上限，並可將連結永久刪除；所有操作寫入 `adminAuditLogs`。
- **統籌人刪除邀請連結**：一般使用者的「邀請連結管理」不再提供單獨保留的「撤銷」流程，改為「撤銷並刪除」；已撤銷的舊資料也可永久刪除。刪除會同時移除 `shortlinks/{code}` 與 `trips/{tripId}/inviteLinks/{code}`，因此原網址立即失效。
- **舊版 6 碼邀請連結**：仍會在行程的邀請連結管理與系統管理者後台明確標示「舊版 6 碼」，可由統籌人或具 `canEdit` 的系統管理員手動刪除。
- **舊版 6 碼跨裝置同步連結**：因同步連結本身沒有行程歸屬，為避免為了列舉清理而暴露其他使用者的同步清單，系統管理員不會看到全部同步資料；具 `canEdit` 的管理員可輸入已知的舊 6 碼代碼進行查詢與永久刪除。舊 6 碼同步代碼即使尚未刪除，也已停止匯入使用。
- **新版代碼維持 12 碼**：新的邀請連結與跨裝置同步連結均使用 12 碼隨機代碼。
- **Firestore Rules**：允許統籌人管理自己行程的邀請連結；系統管理員僅以 `canEdit` 權限讀取／修改／刪除邀請連結。`shortlinks` 仍禁止 `list`，舊版同步連結只能透過已知代碼清理。

### 安全性設計重點

- 邀請連結的兩份資料必須同步處理；刪除採 batch 同時刪除公開解析文件與行程管理鏡像，避免留下可解析但無法管理的孤兒連結。
- 不開放 `shortlinks` 全量列舉，避免系統管理員為了清理同步代碼而取得其他使用者的跨裝置行程清單。
- 舊版 6 碼同步連結採「已知代碼才能清理」的方式；若無法取得代碼，仍可直接在 Firebase Console 的 `shortlinks` 集合手動刪除。
- 系統管理員邀請連結操作均寫入不可修改的 `adminAuditLogs`。

# 旅行行程規劃工具

多人協作的旅遊行程規劃網頁：階層式行程（天 → 時段/景點 → 詳細介紹）、
景點許願池、記帳與自動分帳結算、多行程管理。純網頁，任何裝置用瀏覽器打開連結即可使用，不需要下載 App。

---

## 這個工具的運作方式（先了解，比較好抓 bug）

- **前端**：`index.html` / `style.css` / `app.js`，用 GitHub Pages 免費架設成一個網址。
- **資料庫**：Google **Firebase Firestore**（免費額度），所有行程資料（天數、景點、留言、帳務）即時同步存在這裡，所以每個人打開同一個連結看到的都是最新資料。
- **身分**：**沒有帳號密碼登入**。建立行程時你會列出同行成員名單，之後每個人打開連結，點自己的名字，瀏覽器就會記住「這台裝置是誰」。
- **權限是「軟性」的**：介面上會依權限隱藏/顯示編輯按鈕，但因為沒有真正的登入驗證，技術上沒辦法百分之百防止有人手動修改網址或程式去繞過限制。對朋友、家人的行程規劃來說這通常足夠，但**不要拿來放真正敏感的資料**。
- Firestore 的安全規則（下面會設定）是「知道行程連結的人才能讀寫該行程」，行程彼此之間無法被陌生人任意列出/瀏覽。

---

## Part 1：建立你自己的 Firebase 專案（約 10 分鐘，全部免費）

1. 前往 https://console.firebase.google.com ，用你的 Google 帳號登入。
2. 點「新增專案」，輸入專案名稱（例如 `my-trip-planner`），一路下一步完成建立（Google Analytics 可以關掉，不需要）。
3. 左側選單點 **Build → Firestore Database**，點「建立資料庫」。
   - 位置選離你近的（例如 `asia-east1`）。
   - 安全性規則先選「**測試模式**」，之後我們會換成正式規則（見下方）。
4. 左側選單點 **Build → Authentication**，點「開始使用」，在「Sign-in method」分頁啟用 **匿名（Anonymous）** 登入方式。這個只是讓每個瀏覽器有個內部識別碼，使用者完全不會看到任何登入畫面。
5. 左上角齒輪 → **專案設定**，往下捲到「你的應用程式」，點 `</>`（網頁）圖示，註冊一個應用程式（名稱隨意）。
6. 註冊完成後會顯示一段 `firebaseConfig = {...}` 的設定，把裡面的內容複製起來。

---

## Part 2：把設定貼進程式碼

打開 `firebase-config.js`，找到這段：

```js
const firebaseConfig = {
  apiKey: "YOUR_API_KEY",
  authDomain: "YOUR_PROJECT_ID.firebaseapp.com",
  projectId: "YOUR_PROJECT_ID",
  storageBucket: "YOUR_PROJECT_ID.appspot.com",
  messagingSenderId: "YOUR_SENDER_ID",
  appId: "YOUR_APP_ID",
};
```

把整個物件換成 Firebase 主控台給你的那段設定，存檔。

---

## Part 3：設定 Firestore 安全規則

回到 Firebase 主控台 → Firestore Database → 上方「規則」分頁，把內容整個換成：

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /trips/{tripId} {
      allow get: if request.auth != null;
      allow list: if false;
      allow create: if request.auth != null
        && request.resource.data.name is string
        && request.resource.data.members is list
        && request.resource.data.members.size() > 0;
      allow update: if request.auth != null;
      allow delete: if false;

      match /{document=**} {
        allow read, write: if request.auth != null;
      }
    }

    match /shortlinks/{code} {
      allow get: if request.auth != null;
      allow list: if false;
      allow create: if request.auth != null;
      allow update, delete: if false;
    }
  }
}
```

這組規則的意思：
- 必須先完成 Firebase 匿名登入，才能讀寫資料；未登入的請求會被拒絕。
- `list: false` 會阻止使用者直接列出所有行程或短代碼，降低被批次瀏覽的風險。
- 行程本身禁止整個刪除；天數、景點、留言及帳務等子集合則允許已登入使用者讀寫。
- `shortlinks` 允許已登入使用者查詢與建立短代碼；一般使用者不得修改或刪除既有代碼，行程統籌人可刪除自己行程的邀請連結，具 `canEdit` 的系統管理員可清理已知舊版代碼。

> **重要限制：** 目前網站的成員身份是使用者在瀏覽器內自行選擇的「軟性身份」，沒有把 Firestore 的 `request.auth.uid` 與行程成員綁定。因此這版 Rules 能防止未登入存取、禁止列舉與整個刪除，但還不能做到「只有統籌人可修改」或「每位成員只能修改自己的資料」。若要達成真正的成員級權限，需要進一步改造資料結構與登入／邀請機制。

設定完點「發布」。

---

## Part 4：部署到 GitHub Pages（免費）

1. 到 GitHub 建立一個新的 repository（例如叫 `trip-planner`），設為 Public。
2. 把這個資料夾裡的 4 個檔案上傳上去：
   - `index.html`
   - `style.css`
   - `app.js`
   - `firebase-config.js`（已經填好你自己的設定的版本）
   - `firestore.rules`（建議一併保存，供 Firebase CLI 部署安全規則使用）
3. 上傳完成後，到 repo 的 **Settings → Pages**：
   - Source 選 `Deploy from a branch`
   - Branch 選 `main`／`/(root)`，儲存。
4. 等 1–2 分鐘，頁面上會出現你的網址，長得像：
   `https://你的帳號.github.io/trip-planner/`

打開這個網址，就可以開始建立行程、把連結分享給同行的人了！

> 之後如果要修改程式碼，直接在 GitHub 上編輯檔案存檔，GitHub Pages 會自動重新部署，通常 1 分鐘內生效。

## 已知限制（老實跟你說）

1. **權限是軟性的**：沒有帳密登入，理論上懂技術的人可以繞過介面限制去改資料，也可以隨意切換成別人的身份（右上角切換身份沒有密碼保護）。適合信任的朋友/家人出遊使用，不適合防範惡意使用者。
2. **圖片用網址連結**：因為你選了「貼連結」而不是「上傳檔案」，所以圖片要自己先傳到某個地方（例如 Google 相簿設為公開連結、Imgur 等）取得網址再貼上來。
3. **免費額度**：Firebase 免費方案（Spark）額度給小型使用（幾個人的旅遊行程）綽綽有餘；如果之後想多人大量使用或不放心，可以再升級付費方案，但一般不會需要。
4. **離線無法使用**：需要網路連線才能讀寫資料（跟大部分協作工具一樣）。
5. **「我的行程」清單是裝置本機的**：因為沒有帳號系統，這份清單存在瀏覽器的 localStorage，不會自動跨裝置同步。打開過某行程的連結，該裝置就會記住；也可以用「🔄 跨裝置同步清單」一次把清單帶到另一台裝置。
6. **匯率是「結算時」統一換算，不是每筆消費各自的當天匯率**：新增外幣消費時不會查匯率、也不會卡住；每個幣別的消費會先各自加總，等到看「記帳與分帳」頁面時，才用當下查到（或手動輸入）的最新匯率換算成台幣結算一次。這樣比較穩定（不會因為當天匯率還沒公布而新增不了），但代價是同一幣別的所有消費都用同一個匯率換算，不是每筆各自的歷史匯率。匯率資料存在行程裡，同行的人看到的是同一組數字；可以隨時在「記帳與分帳」頁按「🔄 查詢／更新匯率」重新抓取，查詢用的是 [fawazahmed0/currency-api](https://github.com/fawazahmed0/exchange-api)（免費、不需金鑰）；查不到時可以手動輸入。
7. **外觀設定是裝置本機的**：色彩/字體/字級設定存在瀏覽器裡，換一台裝置或清瀏覽器資料就要重新設定一次，不會影響其他同行人看到的樣子。
8. **短代碼不會自動過期或自動清除；邀請連結現在可由統籌人或管理員手動永久刪除**：每次「分享行程」只會固定用同一組代碼（存在行程資料裡，重複開啟不會一直增加），但「跨裝置同步清單」每按一次「產生同步代碼」都會新建一組。這些代碼會留在 Firestore 裡，數量對免費額度來說完全不是問題，但如果之後想手動清理，可以到 Firestore 主控台的 `shortlinks` 集合裡刪除。
9. **拖曳排序需要支援 HTML5 Drag and Drop 的瀏覽器**：桌面瀏覽器操作較完整；手機瀏覽器若拖曳體驗不佳，仍可使用原有的 ▲▼ 按鈕。
10. **舊版連結依然相容**：如果你在短代碼功能上線前就已經把行程連結、同步連結傳給別人，那些比較長的舊連結（`#/trip/長長的ID` 或網址裡直接帶一長串同步資料）還是可以正常打開，不會因為改版而失效。

## 疑難排解

**點「分享此行程」或「🔄 跨裝置同步清單」，出現「連結產生失敗」／「代碼產生失敗」**

這通常代表 Firestore 的安全規則裡還沒開放 `shortlinks` 這個集合（短代碼／短連結功能會用到它）。請這樣檢查：

1. 到 [Firebase 主控台](https://console.firebase.google.com) → 你的專案 → **Firestore Database → 規則** 分頁。
2. 確認內容裡有包含 `match /shortlinks/{code} { ... }` 這一段（跟 `trips` 那段同一層級）。完整內容看上面「Part 3：設定 Firestore 安全規則」。
3. 如果沒有，把整份規則換成 Part 3 給的完整內容，**按「發布」**，回到網站重新整理頁面再試一次。
4. 如果照著改了還是不行，打開瀏覽器的**開發者工具 → Console** 分頁，找找看有沒有紅字的錯誤訊息（程式碼失敗時會把 Firebase 回傳的原始錯誤印在這裡），那段訊息通常能看出確切原因。

**許願池裡貼的圖片不顯示**

跟一般的內容區塊圖片一樣，是用「貼網址連結」的方式，所以：
- 確認網址是「圖片本身」的直接連結（通常以 `.jpg` / `.png` / `.webp` 等結尾，或是圖床提供的「直接連結」選項），而不是網頁分享連結。
- 有些圖床或社群網站（例如 Instagram）會擋外部網站直接讀取圖片（防盜連），這種情況即使網址正確也可能顯示不出來，建議改用允許外連的圖床，例如 Google 相簿的公開連結、Imgur 等。

## 權限架構更新（Auth Model v2）

本版本開始，新增行程會記錄建立者的 Firebase Authentication UID，並在行程資料中保存 `ownerUid` 與 `access` 權限表，作為後續 Firestore Security Rules 驗證的基礎。

### 重要限制

- 不再提供使用者從成員清單自由切換身份的操作，避免透過前端選擇其他成員而取得其權限。
- 尚未完成 UID 綁定的舊行程，不能直接視為已完成安全遷移；部署新版 Rules 前，請先保留舊規則或完成舊行程遷移流程。
- 本階段已建立新權限模型；舊行程的自行認領功能後續不再提供，現有舊資料由管理員處理。
- 未綁定 UID 的訪客在前端會視為唯讀，但真正的資料安全仍以 Firebase Security Rules 為準。

### 建議部署順序

1. 先在測試 Firebase 專案驗證新版資料結構。
2. 建立新的測試行程，確認建立者 UID 與 `ownerUid`／`access` 正確寫入。
3. 確認統籌人可編輯、未綁定使用者無法寫入。
4. 完成舊行程遷移工具後，再將新版 `firestore.rules` 套用到正式專案。

## Auth Model v2 - Step 3：分享連結與唯讀訪客

本階段將行程的讀取權限與編輯權限分離：

- 已登入且已綁定行程成員 UID 的使用者才能讀取行程主文件；未綁定使用者必須透過有效邀請連結提出加入申請。
- 未綁定 UID 的使用者視為唯讀訪客，不能新增、修改或刪除行程資料。
- `owner` 與 `editor` 的編輯權限仍由行程文件中的 `ownerUid` 與 `access` 控制。
- 行程分享短代碼僅允許該行程統籌人建立；跨裝置同步清單代碼仍可由已登入使用者建立。

目前此模式代表知道行程 ID 或取得分享連結的人可以讀取行程內容，符合本階段「資料不需作為私人資料保護」的使用前提。後續若需要更嚴格的分享控制，再加入邀請碼、到期時間或 Cloud Functions 驗證機制。

### 本階段發布前檢查

1. 先備份目前 Firestore 資料。
2. 將 `firestore.rules` 發布至 Firebase Console。
3. 使用統籌人產生分享連結。
4. 使用另一個瀏覽器或無痕視窗開啟分享連結。
5. 確認可以讀取行程，但看不到新增、編輯、刪除等操作權限。
6. 回到統籌人瀏覽器，確認仍可正常編輯行程。

## Auth Model v2 - Phase 4A：編輯權限申請

本階段新增 `trips/{tripId}/accessRequests/{requestId}`：

- 未綁定 UID 的訪客可以提出編輯權限申請。
- 統籌人可以在「管理成員與權限」查看待審核申請。
- 統籌人選擇要綁定的既有成員後，該 UID 會被設定為 `editor`。
- 拒絕或核准後，申請狀態會被更新。
- 這一階段尚未提供公開邀請連結；先採用「訪客主動申請、統籌人核准」模式，避免前端自行取得編輯權限。

## Auth Model v2 — Step 5: 成員權限管理保護

本階段在既有編輯權限申請流程上，補強統籌人成員資料的保護：

- 儲存成員設定時，必須保留原本 `ownerUid` 對應的成員。
- 一個行程只能保留一位 `owner`，避免在前端操作時意外產生第二位統籌人。
- 更新成員資料時同步保留 `ownerUid` 與 `authModelVersion: 2`。
- 若成員移除 UID 或改為 `viewer`，會同步重建 `access`，讓該 UID 不再擁有編輯權限。

本階段仍未加入正式系統管理員、跨裝置復原或永久邀請碼；這些功能應在目前權限管理流程穩定後再開發。

## 第 11 階段：Firestore Rules 安全強化

本版本調整資料庫安全規則：

- 綁定 UID 的使用者不可透過一般行程更新修改 `ownerUid` 或 `authModelVersion`。
- 非統籌人不可直接修改 `members` 與 `access` 權限資料。
- 舊版行程必須先完成認領，才可新增、修改或刪除 days、spots、wishes 與 expenses 子資料。
- 保留 owner、editor、viewer 及多裝置 UID 的既有權限模式。

部署前請先備份目前 Firebase Console 的 Firestore Rules；部署後應重新測試統籌人、編輯者及唯讀使用者的操作權限。

## 第 12 階段：修正舊行程認領錯誤、邀請連結管理、多裝置 UID 管理

本階段修正一個既有 bug，並完成「邀請連結管理／到期時間」與「多裝置 UID 管理」兩項功能：

**歷史紀錄**：此階段曾修正 `claimLegacyTrip()` 的資料組裝錯誤；該功能已於 v21p3 完整移除，不再提供舊行程自行認領。

**邀請連結管理**（在「管理成員與權限」頁面新增「邀請連結管理」區塊）：
- 可同時建立多組邀請連結（可各自命名用途，例如「家族群組」「朋友群組」）。
- 每組連結可設定到期時間（`datetime-local`），留空表示永久有效；建立後仍可隨時回來調整期限。
- 每組連結可隨時撤銷／恢復啟用，撤銷後訪客再打開該連結會被擋下並提示「已被撤銷」。
- 資料結構：新增 `trips/{tripId}/inviteLinks/{code}` 子集合，作為 `shortlinks/{code}` 的管理用鏡像（因為 `shortlinks` 本身規則禁止 `list`，無法直接列出屬於某行程的所有代碼，所以另存一份在行程底下，只有該行程統籌人可讀取/列出）。撤銷、改期限時兩份會同時更新。
- 舊版「產生邀請連結」按鈕（在「分享此行程」彈窗）已移除單一永久代碼的邏輯，改為導向「管理成員與權限」進行建立與管理。

**多裝置 UID 管理**（同樣在「管理成員與權限」頁面，每位成員列多了一個「🔧 管理裝置」按鈕）：
- 資料模型（`member.uids` 陣列）其實在先前階段已經支援多個 UID 對應同一位成員，但介面上原本只能透過「訪客申請 → 統籌人核准」間接新增，看不到目前綁了哪些 UID，也無法移除。
- 本階段補上介面：展開後可看到該成員目前綁定的所有 UID、手動貼上新的 UID 加入（例如從 Firebase Console 查到的 UID），或移除某個 UID（例如成員換了手機、舊裝置不想再保留登入狀態）。
- 目前登入中且對應 `trip.ownerUid` 的那組 UID 會被保護，無法從介面移除，避免統籌人不小心把自己鎖在外面。
- 新增/移除 UID 後要按最下方「儲存」才會真正寫回 Firestore（跟改名字、改權限是同一個儲存流程）。

### 本階段發布前檢查

1. 先備份目前 Firebase Console 的 Firestore Rules 與資料。
2. 將整份新的 `firestore.rules`（本次新增了 `trips/{tripId}/inviteLinks/{code}` 規則，以及 `shortlinks/{code}` 新增的 `allow update`）發布到 Firebase Console，**注意 README「Part 3」裡的規則片段是很早期的舊版本，不要拿那段去覆蓋，請直接使用專案裡的 `firestore.rules` 檔案內容**。
3. 用統籌人身份打開「管理成員與權限」，確認「邀請連結管理」區塊能正常建立連結、看到清單（如果看到「載入失敗」，代表 Rules 還沒更新）。
4. 建立一組短時間到期的邀請連結（例如 1 分鐘後），用另一個瀏覽器／無痕視窗測試過期後打開會被擋下。
5. 測試撤銷／恢復啟用是否正常運作。
6. 用統籌人身份展開某位成員的「管理裝置」，測試手動新增與移除 UID，確認存檔後該 UID 是否真的取得／失去權限（可以用另一個帳號或無痕視窗實測）。
7. 確認舊行程一般使用者不再出現「認領舊行程」按鈕，且直接開啟舊行程時不會取得 members / access。

## v16 變更

- 權限判斷仍以 Firebase UID、`access` 及 `members[].uid/uids` 為依據，前端隱藏按鈕不視為真正的安全防護。

5. 需以統籌人、編輯者、唯讀成員及未綁定訪客分別確認畫面與 Firestore Rules 行為。
6. 發布規則後，應再以無痕視窗確認未綁定 UID 無法讀取行程內容。

> 注意：目前可稱為功能收尾與安全性補強版本，但尚不能宣稱已完成完整安全稽核。正式上線前仍建議執行 Firebase Emulator／Rules 自動化測試，並完成邀請碼使用次數的原子性控管。

## 第 13 階段：系統管理員與管理後台（第二階段，初版）

本階段實作 v18 目標中的「第二階段」（見下方章節），完成的是**唯讀的行程摘要清單**，
不包含行程停用、稽核紀錄等功能（那些留待後續階段）。新增的檔案完全獨立於既有的
`index.html`／`app.js`／`firebase-config.js`，一般使用者的操作流程沒有任何改變。

### 新增了什麼

- **`admin.html` ＋ `admin.js`**：獨立的管理後台頁面，跟一般行程頁面（`index.html`）分開，
  互不載入對方的程式碼。
- **`admin-firebase-config.js`**：管理後台專用的 Firebase 初始化，用 **Google 登入**
  （`signInWithPopup` + `GoogleAuthProvider`），刻意不共用 `firebase-config.js` 的匿名登入邏輯，
  也不會被一般使用者頁面載入到。
- **`firestore.rules` 新增 `admins/{uid}` 集合**：文件是否存在＝這個 UID 是不是管理員；
  這個集合只能在 **Firebase Console 手動新增/刪除文件**，前端沒有任何寫入權限，也禁止 `list`
  （避免任何人列舉出所有管理員 UID）。
- **`firestore.rules` 新增 `isAdmin()`**，並把 `trips` 的 `allow list` 從 `false` 改成
  `isAdmin()`：只有通過 Google 登入且 UID 在 `admins` 集合裡的人，才能列出所有行程的主文件
  （名稱、成員數、`ownerUid`、建立時間）。**天數／景點／許願池／記帳等子集合的讀取規則完全沒有改動**，
  管理員不會因為這個變更就多出讀寫行程內容的權限；管理後台的「開啟行程」連結只是把管理員導到跟一般
  訪客一樣的畫面，要看到完整內容仍然要被行程統籌人加進成員名單。

### 這一版管理後台能做什麼／不能做什麼

- ✅ 用管理員自己的 Google 帳號登入（不是匿名登入，不會因為換瀏覽器、清資料而換人）。
- ✅ 看到所有行程的清單：行程名稱、成員數、建立時間、狀態（啟用中／已停用）、行程 ID。
- ✅ **不用加入行程、不用被統籌人綁定成員身份，就能直接在管理後台裡唯讀檢視任何一個行程的完整內容**：
  成員與權限、每天的天數與景點（含內容區塊：文字／圖片／表格）、每個景點的許願池留言、完整記帳明細。
  這是直接在 `admin.html` 裡渲染出來的，不是連去 `index.html`——因為 `index.html` 用的是匿名登入，
  跟管理後台的 Google 登入是兩回事（見下方「重要：管理員身份跟『行程裡的身份』是分開的」）。
  管理後台本身**完全沒有編輯功能**，只能看。
- ✅ **可以停用／恢復啟用任一行程**：停用後，包含統籌人在內的所有一般使用者都無法再新增、修改、刪除
  天數、景點、許願池留言、記帳明細，也不能改行程名稱等主文件欄位；打開該行程會看到「已被系統管理員停用」
  的提示畫面。只有管理員能把它改回啟用，改回去之後原本的成員與權限照舊生效，不會遺失任何資料。
- ✅ 清單裡仍保留「開啟行程」連結（用一般模式打開 `index.html`），方便你用自己原本的成員身份操作，
  跟管理後台的唯讀檢視是两條互不影響的路徑。
- ✅ 非管理員（沒登入、登入了但 UID 不在 `admins` 集合）看到的都是唯讀的提示畫面，看不到清單。
- ❌ 還不能直接刪除行程（只能停用）。
- ❌ 還沒有操作稽核紀錄（誰在什麼時候停用/恢復了哪個行程，目前只記在該行程文件的 `disabledBy`／`disabledAt`
  兩個欄位，沒有獨立的稽核紀錄集合）。
- ❌ 管理後台本身不能編輯行程內容（新增/修改/刪除天數、景點、留言、帳務）；要編輯還是得透過一般行程頁面
  並且是該行程的成員。這是刻意保留的邊界，避免管理員權限擴散成「可以動任何人資料」。

### 重要：管理員身份跟「行程裡的身份」是分開的

用同一個瀏覽器，`admin.html` 用 Google 登入、`index.html` 用匿名登入，兩者是完全不同的 Firebase Auth
session，彼此不知道對方的存在。所以從管理後台的「開啟行程」連結打開 `index.html` 時，看到的還是**這個
瀏覽器原本的匿名身份**對這個行程的權限（如果你自己就是統籌人，會直接看到完整內容；如果不是，會看到
「尚未綁定身份」畫面）——這是預期行為，不是 bug。真正不需要加入就能看到內容的入口，是管理後台裡的
「檢視內容」按鈕，不是「開啟行程」連結。

### 設定步驟（請照順序做）

**1. 在 Firebase 啟用 Google 登入**
   - 到 [Firebase 主控台](https://console.firebase.google.com) → 你的專案 → **Authentication → Sign-in method**。
   - 啟用 **Google**，選一個「專案支援電子郵件」存檔即可，其他選項用預設值。
   - 到 **Authentication → Settings → Authorized domains**，確認你的 GitHub Pages 網域
     （例如 `你的帳號.github.io`）有在清單裡；沒有的話按「新增網域」加進去，否則 Google 登入彈窗會失敗。

**2. 發布新的 `firestore.rules`**
   - 打開專案裡的 `firestore.rules`（不是 README 裡任何片段），整份複製。
   - Firebase Console → **Firestore Database → 規則**，貼上覆蓋，按「發布」。
   - 這次規則更新新增了：管理員可以唯讀讀取任何行程的 `days`/`spots`/`wishes`/`expenses`；管理員可以
     切換行程的 `disabled` 欄位；`disabled: true` 的行程會擋下所有一般使用者（含統籌人）的寫入。
     沒有 `disabled` 欄位的既有行程完全不受影響。

**3. 把 `admin.html`、`admin.js`、`admin-firebase-config.js`、`app.js`、`firestore.rules` 上傳到你的 GitHub repo**
   - 這次 `app.js` 也有修改（新增「行程已停用」的提示畫面），需要重新上傳；其餘既有檔案
     （`index.html`、`style.css`、`firebase-config.js`）沒有變動，不用重傳。
   - 等 GitHub Pages 部署完（通常 1 分鐘內），用瀏覽器打開
     `https://你的帳號.github.io/trip-planner/admin.html`。

**4. 第一次登入、取得自己的 UID**
   - 打開 `admin.html`，按「使用 Google 帳號登入」，用你要當管理員的那個 Google 帳號登入。
   - 這時候畫面會顯示「沒有管理員權限」，因為 `admins` 集合裡還沒有任何文件——這是預期行為。
   - 畫面上會顯示一串 UID，把它複製起來。

**5. 在 Firebase Console 手動把自己加為管理員**
   - Firebase Console → **Firestore Database → 資料**分頁 → 「開始蒐集」（或「新增集合」）。
   - 集合 ID 填 `admins`。
   - 文件 ID 貼上剛剛複製的 UID（**不要用自動 ID**，一定要手動貼成文件 ID）。
   - 欄位隨意，例如加一個 `note`（字串）填你的名字方便日後辨識；也可以完全不加欄位，空文件也算「存在」。
   - 存檔。

**6. 回到 `admin.html` 重新整理頁面**
   - 應該會直接進入管理後台，看到所有行程的清單。
   - 如果還是顯示「沒有管理員權限」：確認 Rules 已經按過「發布」、確認 Firestore 裡 `admins`
     集合的文件 ID 跟畫面顯示的 UID 完全一致（不要多空白），也可以按「登出」再重新登入一次。

**7. 之後要新增其他管理員**
   - 請他們打開 `admin.html`、登入他們自己的 Google 帳號，把畫面上顯示的 UID 給你。
   - 你到 Firebase Console 的 `admins` 集合，用同樣方式新增一筆文件（文件 ID＝他的 UID）。
   - 要移除某人的管理員權限，直接在 Firebase Console 把對應文件刪除即可，不需要改程式碼或 Rules。

### 發布後請測試

1. 用還沒加進 `admins` 的 Google 帳號登入 `admin.html`，確認只會看到「沒有管理員權限」畫面，
   看不到任何行程清單。
2. 用已加進 `admins` 的帳號登入，確認能看到所有行程的名稱／成員數／建立時間／狀態。
3. 按某個行程的「檢視內容」，確認能唯讀看到成員清單、天數、景點、內容區塊、許願池留言、記帳明細，
   且沒有任何可以編輯的按鈕。
4. 從清單按「開啟行程」，確認打開的是一般的 `index.html` 畫面，且（在還沒被該行程統籌人加為成員的情況下）
   看到的是「尚未綁定身份／申請加入」畫面，不是完整行程內容。
5. 找一個測試用的行程按「停用」，確認：
   - 管理後台的狀態欄立刻變成「已停用」。
   - 用該行程統籌人的瀏覽器打開這個行程，看到的是「此行程已被系統管理員停用」畫面，看不到原本內容，
     也無法新增/編輯任何東西。
   - 回到管理後台按「恢復啟用」，統籌人重新整理頁面後應該能恢復看到原本內容，成員與權限都還在。
6. 回到一般使用者流程（不透過 `admin.html`，直接用行程連結或邀請連結），確認建立行程、加入行程、編輯、
   記帳等既有功能在「未停用」狀態下都跟之前一樣正常，沒有受到這次修改影響。

## 第 14 階段：管理員編輯權限、稽核紀錄與後台優化（v17p7）

> 第 13 階段寫的「管理後台完全沒有編輯功能」在本階段起已更新：有編輯權限的管理員可在 `admin.html` 內做「救援型」編輯。

### 新增與調整

- **管理員分級**：`admins/{uid}` 文件加布林欄位 `canEdit: true`（在 Firebase Console 手動設定）才有編輯權；沒設定的管理員仍是唯讀＋停用／恢復，畫面上也不會出現編輯按鈕。
- **`isAdmin()` 只認 Google 登入**：Rules 加上 `sign_in_provider == 'google.com'`，匿名身份不可能被當成管理員。
- **可編輯範圍（`isAdminEditor()`）**：修改行程名稱（僅 `name`）、編輯景點名稱／時間、編輯文字區塊或移除區塊、刪除景點（連同留言）、刪除許願池留言、刪除記帳明細。成員權限與 UID 需另有 `canManageMembers` 才能改（見第 15 階段）。管理員編輯不受行程停用限制（方便停用後清理內容）。
- **稽核紀錄 `adminAuditLogs`**：停用／恢復、所有編輯、匯出都會在同一個 batch 寫入一筆紀錄（管理員、時間、動作、行程、內容）。Rules 只允許管理員讀取與新增，不可修改或刪除；後台首頁有「稽核紀錄」按鈕可看最近 100 筆。
- **匯出 JSON**：行程詳細頁「⬇ 匯出 JSON」，包含主文件、天數、景點、內容區塊、許願池留言與記帳（匯出動作本身也會留紀錄）。
- **效能**：檢視內容時不再對每個景點都查一次許願池，改成點「載入許願池留言」才讀。
- **停用功能**：可填停用原因（`disabledReason`）；恢復啟用時 `disabledAt` 清為 `null`，不再被誤更新成現在時間。
- **清單**：可搜尋行程名稱／ID、篩選啟用／停用，並顯示統籌人；成員表顯示綁定的 UID（協助救援換手機的統籌人）。
- **共用設定**：Firebase 設定集中到 `firebase-options.js`，`firebase-config.js` 與 `admin-firebase-config.js` 都從這裡 import，之後只改一份。
- **Rules 欄位驗證**：`days`／`spots` 寫入加上寬鬆的 `validContentDoc`（title 為字串且 ≤ 500 字、blocks 為陣列且 ≤ 500 個）。

### 部署步驟（請照順序）

1. 上傳／覆蓋：`firebase-options.js`（新）、`firebase-config.js`、`admin-firebase-config.js`、`admin.js`、`firestore.rules`。
2. Firebase Console → Firestore → 規則：貼上新的 `firestore.rules` 並按「發布」。
3. Firebase Console → Firestore → `admins/{你的 UID}` 文件：新增欄位 `canEdit`（型別 boolean）＝ `true`。
4. 重新整理 `admin.html`，確認詳細頁出現「你的帳號具有編輯權限」。

### 發布前手動測試

- 沒有 `canEdit` 的管理員：可看、可停用／恢復、可匯出，看不到編輯按鈕，直接呼叫寫入會被 Rules 拒絕。
- 有 `canEdit` 的管理員：逐一測改名、改景點、編輯／移除區塊、刪景點、刪留言、刪記帳，並在「稽核紀錄」確認每筆都有紀錄。
- 一般使用者五種身份（統籌人、編輯者、唯讀成員、未綁定訪客、匿名）在一般頁面的新增／編輯／留言／記帳流程都沒有變化，且 `days`／`spots` 正常儲存（驗證寬鬆，理論上不受影響）。
- 停用行程後：一般成員無法寫入、管理員（canEdit）仍可編輯，恢復後成員照舊。

### 尚未完成／注意

- 管理員的 Google 帳號請開啟兩步驟驗證；`admins` 名單與 `canEdit` 只給必要的人。
- 稽核紀錄目前由前端在同一個 batch 寫入，Rules 只保證「不可竄改」，並不能強制「每次編輯一定有紀錄」。
- 行程軟刪除與成員權限／UID 編輯已在第 15 階段完成；尚未做：JSON 匯入（優先級較低，之後補）、Firebase Emulator 自動化測試。

## 第 15 階段：行程軟刪除、管理員編輯成員權限與 UID（v17p8）

### 新增

- **行程軟刪除／還原**（需 `canEdit: true`）：管理後台清單的「刪除」／「還原」，或詳細頁按鈕。只寫入 `deleted`、`deletedAt`、`deletedBy`、`deletedReason`，**資料完全保留**。清單新增「已刪除」分類；「全部」預設不含已刪除行程。
- **一般使用者端**：`app.js` 遇到 `deleted === true` 的行程，會從本機「我的行程」移除，只顯示「此行程已被刪除」，不訂閱任何內容。Rules 端也把已刪除視同停用：成員讀不到內容、任何一般角色都不能寫入，只有管理員能還原。
- **編輯成員權限與 UID**（需 `canManageMembers: true`，與 `canEdit` 分開）：詳細頁「🔑 編輯成員權限／UID」。可改每位成員的權限、新增或移除綁定的 UID。規則：行程必須恰有一位統籌人（選另一人當統籌人會自動把原統籌人降為可編輯）、統籌人至少一個 UID、同一 UID 只能屬於一位成員、UID 格式檢查、儲存前會確認「成員資料未被別人同時修改」。前端會同步重建 `access` 與 `ownerUid`；Rules 要求 `members`／`access`／`ownerUid` 一起改，且新的 `ownerUid` 在 `access` 中必須是 `owner`。
- **主網頁入口**：左側選單最下方新增「🛠️ 管理員後台」按鈕（新分頁開啟 `admin.html`）。按鈕對所有人可見，但頁面本身仍需 Google 登入，且要在 `admins` 名單內才看得到內容。
- 兩項操作都寫入 `adminAuditLogs`（`trip-delete`／`trip-restore`／`members-update`，含每位成員權限與 UID 的增減）。
- 舊版行程（尚未完成 Auth Model v2、沒有 `access`／`ownerUid`）不開放一般使用者存取；請由管理員處理或重新建立。

### 部署步驟（請照順序）

1. 上傳／覆蓋：`admin.js`、`app.js`、`firestore.rules`（其他檔案沿用 v17p7）。
2. Firebase Console 貼上新的 `firestore.rules` 並「發布」。
3. `admins/{你的 UID}` 文件：確認 `canEdit` 為 `true`；要能改成員／UID 再新增布林欄位 `canManageMembers` ＝ `true`。
4. 重新整理 `admin.html` 與 `index.html`。

### 發布前手動測試

- 軟刪除：刪除後，該行程的統籌人／成員在一般頁面看到「已被刪除」且左側清單消失；管理員在「已刪除」分類仍可檢視、匯出、還原；還原後成員照舊。
- 成員編輯：改一位成員權限、新增 UID 後，該 UID 的裝置立刻取得對應權限；移除 UID 後立刻失去；更換統籌人後，新統籌人可管理成員、原統籌人變為可編輯。
- 沒有 `canManageMembers` 的管理員看不到編輯按鈕，直接寫入會被 Rules 拒絕。
- 一般使用者的建立行程、加入、編輯、留言、記帳流程沒有變化。

### 尚未完成／注意

- 「永久刪除」（真正清除資料）沒有做，Rules 仍是 `delete: false`；軟刪除的行程與子集合會一直留在 Firestore。
- 尚未做：JSON 匯入（優先級較低）、Firebase Emulator 自動化測試。
- 管理員可更換行程統籌人與任意綁定 UID，等於能決定誰能編輯行程，請把 `canManageMembers` 只給必要的人。

## 第 16 階段：免費方案內的安全強化（v17p10）

> 這一版的優化都不需要升級 Firebase 付費方案（Blaze）：雙重驗證（Identity Platform）與自動排程備份（需要 Cloud Functions／Scheduler）目前先不做。

補充一點：Firebase **Local Emulator Suite**（本機模擬測試環境）本身是完全免費的，不需要 Blaze 方案，只是需要在本機安裝 `firebase-tools`。如果之後想做 Rules 自動化測試，這項不受付費限制，可以再評估。

### 新增

- **高風險操作要求最近重新登入**：刪除／還原行程、更新成員權限與 UID，這兩類操作現在需要 15 分鐘內重新登入過 Google 帳號，Rules 端用 `recentlyAuthenticated()`（比對 token 的 `auth_time`）把關，前端也會先跳出提示、引導重新登入一次，避免半路被 Rules 拒絕才發現。這個機制完全用 Firebase Authentication 內建欄位，不需要額外付費功能。
- **手動全站備份**：管理後台首頁新增「💾 匯出全部行程備份」，一次讀取所有未刪除行程的完整內容（含天數、景點、留言、記帳），下載成單一 JSON 檔。取代需要 Blaze 方案的「排程自動匯出」，改成人工定期點擊執行（建議自己排個頻率，例如每週手動備份一次）。備份動作本身也會留稽核紀錄。

### 部署步驟

1. 上傳／覆蓋：`admin.js`、`firestore.rules`（其他檔案沿用 v17p9）。
2. Firebase Console 貼上新的 `firestore.rules` 並「發布」。
3. 重新整理 `admin.html`。

### 發布前手動測試

- 登入後立刻刪除行程／改成員，應該直接成功（剛登入在 15 分鐘內）。
- 等 15 分鐘以上（或用開發工具修改本機時間／直接改 Rules 常數縮短成 1 分鐘測試）再操作，應該會跳出「需要重新驗證」的提示，按確認後跳出 Google 登入視窗，完成後操作能正常送出。
- 取消重新登入的提示，應該不會送出任何寫入。
- 「匯出全部行程備份」在行程數量多時仍能完整跑完並下載成功，按鈕過程中會顯示進度且不能重複點擊。

### 尚未完成／注意

- 雙重驗證（2FA 強制）、自動排程備份、JSON 匯入、Firebase Emulator 自動化測試仍未做，前三項中雙重驗證與排程備份需要 Blaze 付費方案；Emulator 測試不需要付費，是之後可以優先考慮的項目。
- 「15 分鐘」的門檻寫死在 Rules 與前端，之後如果要調整，兩邊都要一起改。

## 第 17 階段：邀請連結次數上限（v17p13）

### 做法

- 沿用現有「申請加入 → 統籌人核准」流程（本來就不是連結打開就自動取得權限），所以不需要 Cloud Functions，也不會被訪客端偽造次數：**次數是用「已核准的申請數」統計出來的，寫入 `access` 的動作本身就只有統籌人能做**。
- 邀請連結的次數上限（`maxUses`）跟到期時間（`expiresAt`）用同一套「手動調整」邏輯：建立時可留空（預設無限次），事後也能隨時在「管理成員與權限 → 邀請連結管理」調整或清空（清空＝改回無限次）。
- 送出申請時會記錄是透過哪一組邀請連結代碼進來的（`accessRequests/{uid}.inviteCode`）。統籌人審核「待核准」清單時，畫面會顯示這組連結目前已核准幾次／上限幾次；如果已經達到上限，「核准」按鈕按下去會再跳出一次確認，統籌人仍可選擇超額核准（畢竟是自己設的上限，最終決定權在人，不是寫死擋死）。
- 沒有透過邀請連結、直接用行程 ID／舊連結申請的請求，`inviteCode` 為 `null`，不受任何連結的次數限制。

### 部署步驟

1. 上傳／覆蓋：`app.js`、`firestore.rules`（其他檔案沿用 v17p12）。
2. Firebase Console 貼上新的 `firestore.rules` 並「發布」。
3. 重新整理 `index.html`。

### 發布前手動測試

- 建立一組邀請連結時設定次數上限（例如 2），核准 2 筆申請後，第 3 筆待核准申請應該會顯示「已達上限」的提示，核准前會多跳出一次確認。
- 把同一組連結的次數上限改大或清空，第 3 筆應該就能正常核准，不再跳確認。
- 不設上限（留空）的連結，核准多少次都不會出現提示。
- 舊有的、還沒有 `inviteCode` 欄位的既有申請資料，審核畫面不會報錯，也不受任何次數限制（維持原行為）。

### 尚未完成／注意

- 這個機制仍然要靠統籌人自己去看「待核准」清單、自己按核准，不是訪客打開連結就自動計數擋下，跟 README 第三階段原本設想的「以核准人數統計」做法一致，免費方案內可行的做法大概就是這樣。
- 如果之後想要「連結打開就直接自動加入、不用人工核准」，那就必須做後端（Cloud Functions）驗證與原子計數，屬於付費方案的範圍，目前先不做。

## 各階段的架構與實施方法

**第一階段收尾（純 Rules 與前端，無需後端）**
Rules 以行程文件的 `access` 對照表判斷角色，前端 `myMember()` 用同一份資料決定畫面。要維持的原則是：**所有權限判斷都放在 Rules，前端隱藏按鈕只是體驗**。

**第二階段：管理員**
1. 管理員不能用匿名登入（換瀏覽器 UID 就變了）。在 Firebase Authentication 啟用 Google（或 Email/密碼）登入，只給管理員用。
2. 建立 `admins/{uid}` 集合，由你在 Firebase Console 手動新增管理員的 UID，不開放任何寫入。
3. Rules 加入 `function isAdmin() { return signedIn() && exists(/databases/$(database)/documents/admins/$(request.auth.uid)); }`，並讓 `trips` 的 `list` 與讀取允許 `isAdmin()`；是否允許管理員寫入視需求另定。
4. 新增獨立頁面 `admin.html` + `admin.js`，與一般行程頁分開；只列出行程（名稱、成員數、建立時間）並可進入檢視。
注意：管理員頁面若要讀所有行程內容，必須同時修改 Rules，前端無法自行繞過。

**第三階段：邀請碼使用限制與可編輯邀請**
- 訪客無法更新 `shortlinks`（規則只允許統籌人），所以「次數」不能由訪客端遞增。可行做法：申請文件 `accessRequests` 記錄 `inviteCode`，統籌人核准時統計該 code 已核准人數，超過 `maxUses` 就禁止核准／自動失效。
- 若要「連結直接給編輯權」，必須由後端（Cloud Function）驗證邀請碼後代為寫入 `access`，因為前端無法安全地自行授權。在沒有後端前，維持「申請＋核准」是最安全的做法。

**第四階段：跨裝置**
1. 備份匯出／匯入（低複雜度，優先）：統籌人把行程主文件、days、spots（含 wishes）、expenses 讀成一份 JSON 下載；匯入時建立新行程，匯入者成為統籌人，成員 UID 綁定清空（避免帶入舊 UID）。
2. 恢復金鑰／QR：可用「一次性恢復碼」由統籌人替成員產生，但兌換時要有人寫入 `access`，同樣需要後端才安全；在沒有後端時，QR Code 只能用來傳 UID 或邀請連結，等於現有流程的包裝。
3. 自動恢復：Cloud Functions 兌換金鑰 → 把新裝置 UID 加入該成員的 `uids` 與 `access`，並使舊金鑰失效。

### 發布前必要測試

1. 未綁定訪客不能直接讀取行程主文件或行程內容；持有效邀請連結者只能提出加入申請。
2. viewer 可以新增、修改與刪除自己的許願池留言，但不能修改其他人的留言。
3. viewer 可以新增與管理自己建立的記帳明細，但不能修改其他人的明細。
4. editor 只能修改規定的行程主文件欄位，不能自行變更 `members`、`access`、`ownerUid`。
5. 管理員的停用／恢復、軟刪除／還原、成員 UID 管理均須符合對應權限與重新驗證時間限制。
6. 邀請連結由統籌人建立與管理；系統管理員具 `canEdit` 時可從管理後台維護／清理，訪客不得更新 `shortlinks`。
7. 所有批次寫入都必須逐筆確認其目標集合具有對應的 Rules 防護。
